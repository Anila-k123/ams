# CLAUDE.md

Guidance for Claude Code when working in this repository (AMS — Advocate Management System).

## Documentation rule (always follow)

- **Keep this file current.** When a change alters architecture, commands, conventions, env vars, or gotchas listed here, update CLAUDE.md in the same change.
- **Keep `docs/` current.** Feature, operations, or design changes must be reflected in the relevant Markdown file under `docs/` (or the root docs listed below). Add a new `docs/*.md` for a new feature area rather than leaving it undocumented.
- Update docs as part of the task, not as a follow-up.

## Commands

Start everything (Windows): `run-project.bat` (scraper + scheduler + backend + frontend in separate windows; it skips the scraper/scheduler if they're already running).

Dev instance beside the test one (same machine): `run-dev.bat` — backend 8081, frontend 5174, DB `pactpro_db1`, emails to console, no scraper/scheduler (the test instance owns 8080/5173/`PactPro_db` and its scheduler). Without the scheduler, in-app (bell) notifications stay queued: run `manage.py process_notifications` to deliver them.

Background processes: `tools\install-services.ps1` registers **PactPro Scraper**, **PactPro Scheduler** and **PactPro Order Sync** (`manage.py run_order_sync`: new court orders for imported cases every 30 min Mon-Sat 10:00-18:00 and at 19:30, saved to the case and announced to the team and the client; offline cases with a CNR are linked to their court record once a day (`courtsearch/linking.py`, also the case page's Link to court record by CNR or SC diary no.); one fetch per court case (CNR / diary no.) however many firms track it, `ORDER_SYNC_WORKERS` in parallel, quiet cases daily, disposed weekly, stopped firms skipped; `docs/ORDER_SYNC.md`) as sign-in tasks, and **PactPro Cause List Sync** (daily 06:30 and 12:30, `scripts\sync_causelist.bat`). Each runs under `tools\keepalive.ps1`, which restarts it whenever it stops and logs to `logs\<Name>.log`. Use `-Status` to check and `-Uninstall` to remove. Without the scheduler, no hearing, overdue-invoice or task-deadline reminders are sent.

Phase 1 (`drafting/onlyoffice.py`, `DraftFile`): with `DRAFT_EDITOR=onlyoffice` the draft page edits the Word file in ONLYOFFICE, and `render_draft_docx` returns that file (forced save first). The file / callback endpoints are public API views checked by signed link + JWT, outside the client gate (the gate test skips public views). After changing `.env`, restart the backend: settings aren't reloaded. Phase 2 (`drafting/docfile.py`): each clause is a locked content control tagged `pactpro:block:<id>` (recorded by both renderers only while `ensure_file` sets `docfile.building`), placeholders are `[[Label]]` in the file, and every save copies clause text back into the blocks (`sync_blocks`), so Lisa / search / compare keep working; the Placeholders panel fills the file (`onlyoffice/placeholders/`). New drafts' blanks are Word form fields (content controls tagged `pactpro:field:<Label>`, made by `docfile.tokens_to_fields` in `ensure_file`; read / filled / changed with `docfile.fields` / `fill_fields`); older drafts keep `[[Label]]` text and both are filled by the same Apply. **Ask Lisa on an ONLYOFFICE draft** (`views.assist`, `services/doc_edits.py`): the model returns find / replace edits on numbered paragraphs of the Word file, never rewritten clauses; every edit is checked against the file before it is shown and again when written (`docfile.apply_edits`), the same value elsewhere is found by search, and an ambiguous instruction gets a question back. Don't go back to "rewrite the clause and diff it" for these. Phase 3: `onlyoffice.editor_role` gives decide / suggest (review-only, edits tracked) / view from `access.can_write` / `can_suggest`; open tracked changes and comment threads in the Word file (`docfile.review_state`) block Approve via `task_review.approve_blockers`, open changes block Submit. **Any AMS document** opens in the same editor (`documents/editor.py`, page `DocumentEditorPage.tsx`, `/dashboard/documents/<id>/edit`; New document = `POST /api/documents/new`): each save is a document version via `storage.add_version`; editor key / change data live in side tables `document_edit_state` / `document_version_changes`; access = practice scope + `DOCUMENT_VIEW` / `DOCUMENT_EDIT`. **Desktop editing** (`documents/dav.py`, docs/DESKTOP_EDITING.md): `/dav/<signed token>/<name>` is a public WebDAV endpoint (no AMS login; the token carries kind / id / user / edit); **only Save to PactPro makes a version**: a desktop Save (`PUT`), the PactPro editor's own Save / Ctrl+S / closing (callbacks without `userdata: 'pactpro'`) and Download only overwrite a working copy (`desktop_work`) that becomes one version on PactPro's Save or **Save to PactPro** (`/api/desktop-work`, `components/DesktopEditsBar.tsx` on every page); a desktop `LOCK` (`desktop_lock`) or a waiting working copy makes both PactPro editors read-only (`editor_role(..., desktop=False)` is how WebDAV itself checks rights); `GET /api/desktop-links` gives the `ms-word:` / `vnd.libreoffice.command:` links. Front end: `useOpenWith` (`components/OpenWithDialog.tsx`) for every Open, `useSaveChoice` for PactPro's Save. **Task documents:** a task keeps its document: **Continue document** (`components/TaskDocument.tsx`) reopens the attached one instead of making a new one; the task API's `documents` carry `version` / `editable` / `pendingWork` (task views pass `context={'request': request}`); the document editor's **Submit to task** (assignee of a delegated task, `documents.editor._tasks_of`) saves to PactPro then submits. A submission hands in chosen documents only (`documentIds`, stored with versions in `TaskSubmission.documents`); the rest are reference, and approval marks only the latest submission's documents Approved (`review.approve`). **Save to PactPro inside the desktop program:** `desktop-addins/` (LibreOffice extension `pactpro.oxt`: a **PactPro** toolbar button opening one window that shows only the actions this person may take, plus a menu; Office add-in manifest + task pane in `public/addins/word/`; bump `description.xml`'s version on each change), built by `python desktop-addins/build.py [--web https://… --api https://…]` into `public/addins/`; they call `<file folder>/.pactpro/save|discard|status|submit|review` with the file's own WebDAV token (submit / review run `workspace.views.submit_task` / `review_task`, shared with the pages). The Office add-in needs HTTPS. Drafts in the add-ons hand in through `drafting.filing.file_draft` (shared with the page's Submit to task). **Blank documents:** New document / Write in editor mark the document `DocumentEditState.blank`; closed never-saved (editor status 4, WebDAV UNLOCK) it is removed via `documents.views.remove_document` (`documents/blank.py`), and the scheduler's scan runs `manage.py remove_blank_documents` for leftovers older than a day.

LibreOffice is a server prerequisite (Download → PDF, View print preview, and the ONLYOFFICE draft redline in its own look: Compare Document via LibreOffice's Python, `drafting/export/libre_redline.py`, `LIBREOFFICE_PYTHON`, Linux `python3-uno`; it falls back to the standard-layout redline), installed by `tools\install-libreoffice.ps1` / `tools/install-libreoffice.sh` (docs/DEPLOYMENT.md 1a); `manage.py check_pdf_export` verifies a server can make PDFs.

## Backend architecture

- Project package: `advocate_backend/` (settings, urls). One Django app per domain: `accounts`, `clients`, `cases`, `events`, `documents`, `dashboard`, `notifications`, `rbac`, `expenses`, `invoices` (GST), `payments`, `search`, `reports`, `audit`, `backup`, `communication`, `assistant` (LLM), `appeals` (decided cases on Appeal Alerts: who won, our side, can-appeal / other-side-may / needs-a-look, evening appeal watch; never tells the client; no limitation dates yet; docs/APPEALS.md), `workspace` (display board, tasks/review), `courtsearch`, `acts`, `dictionary`, `drafting`, `clientaccess`, `lawcodes` (BNS), `firms` (teams grouped into a firm, `firm_team`), `metering` (AI token usage per feature, `llm_usage`), `clientreview` (documents sent to the client for review, docs/CLIENT_REVIEW.md: the client downloads a cleaned copy, edits it in their own Word and uploads it back (the portal editor in review mode is built but off: `CLIENT_REVIEW_EDITOR`), `/api/client/reviews…`, editor links `/api/editor/clientcopy/…`; new notification types widened in `clientreview/0002`), `core` (shared helpers, `practice.py` tenancy, `finance.py` case money totals).
- **SaaS tenancy (Phase 2, `docs/TENANCY.md`):** `firms.Firm` is the tenant, `FirmMembership` links identities to it, `FirmSettings` holds firm details; business tables carry `firm_id` (children inherit via parent). Access = active membership of an active firm + `firm_id` ownership + permissions + team scope. Never take a firm from the request: use `core/tenant.py` (`resolve_firm`, `owned(qs, user)`, `team_scope`). New tenant-owned querysets in views must go through `owned(...)`; new tenant models need a conditional `firm_id` (`if settings.TENANCY_COLUMNS:`) and an `OWNED`/`DERIVED` entry in `firms/tenancy.py`; bulk/raw inserts must set `firm_id` themselves (pre_save `stamp_firm` doesn't run). `TENANCY_MODE` legacy (default) / shadow / firm; `TENANCY_COLUMNS` on once the tenancy migrations are applied to that database (tests and makemigrations always on; tests always start in legacy mode). Account ids differ per developer database: each developer drafts their own mapping (`plan_tenancy --suggest firms/tenancy_mapping.local.json`, git-ignored), reviews it, then `plan_tenancy` -> `apply_tenancy --yes` (`--allow-database PactPro_db` needed for a database with that name) -> `verify_tenancy`, then shadow, then firm.
- **Teams and firms:** a team = a practice root (`parent_advocate_id` NULL) + its members; `firms.FirmTeam` groups teams into one firm. `practice_ids(user)` returns the user's own team, or every team of the firm for firm-wide roles (Super Admin, Accountant). One senior's team must never see another senior's cases. That covers everything on a case (tasks, notes, parties, documents, events, money, client). A case id from outside the user's reach is refused with a 404, never silently dropped: an expense once got saved unlinked that way. `core/test_team_isolation.py` pins this down. `manage.py make_team` splits a senior out into their own team. `manage.py create_firm` starts a **separate firm** (its own Super Admin, optional seniors); Users → Add User can't, since it always joins the creating admin's firm. User management is per firm too: `/api/admin/users…` only lists and changes accounts of the admin's own firm (`rbac.views._firm_users`); another firm's user is a 404. New people are only invited (`/api/firm/invitations`, they set their own password); `POST /api/admin/users` answers 410 `USE_INVITATION`.
- **Unmanaged models:** most models map onto tables from the original Spring app and are `managed = False` — no migrations for them; the DB must already exist. Newer tables are managed normally. To add data to a Spring-owned table, add a small managed side table keyed by the row id (e.g. `clients.ClientHandler` → `client_handler`) rather than altering it.
- **Tests** use `core.test_runner.ManagedModelTestRunner`, which flips unmanaged models to managed and builds tables from models (not migrations). Live-DB CHECK constraints are *not* reproduced in tests.
- **No scraping code in the backend.** It proxies/caches/stores/matches data from the scraper service (see `ARCHITECTURE.md`). Shared caches must never contain per-practice data — apply practice overlays after cache reads.
- **LLM assistant (Lisa)** — see `docs/AI_ASSISTANT.md`. `assistant/planner.py` answers chat (tool calling for openai/gemini, else the `context.py` brief), `tools.py` holds every lookup with its permission (`_CATALOGUE`), `privacy.py` masks, `provider.py` talks to the model (`LLM_PROVIDER`, `ASSISTANT_TOOL_CALLING`). New data or a new action for Lisa = a new `_CATALOGUE` entry with its permission, not a new block in the prompt. **Never add phrase rules for typed text**: typed messages always go to the AI; `/api/assistant/query` is for quick-button command names and the basic-mode fallback only.
- **Assistant access rule:** Lisa must never show what the user's own pages would refuse. Data reaches the prompt only through `assistant/tools.py`, inside `tools.acting_as(request.user)`; gate each block with `tools.allowed(advocate_id, <PERMISSION>)` (and `TOOL_PERMISSIONS` for tools). No process-wide caches of scope or permissions.
- **Assistant masking:** everything Lisa sends to a model goes through `assistant.privacy.Masker` (built with `Masker.for_user`), and replies through `StreamUnmasker`. Forced on for external providers (`llm.EXTERNAL_PROVIDERS`). New prompt content must be masked too; never log prompts or replies (log sizes only).
- **Drafting / summaries and external AI:** every drafting model call goes through `LLMProvider.complete`, which asks `drafting/providers/privacy.py::guard()`: a model outside this machine / the office network only gets text masked with the acting advocate's vocabulary plus the draft's fact names (`names_for_masking`), the reply is unmasked; with no acting user (no `metering(...)` context) or a known value still visible after masking it raises `ExternalAIBlocked` instead of sending. New drafting LLM entry points must run inside `metering(feature, op, advocate_id)`. `DRAFTING_MASK_EXTERNAL=False` sends originals (approved decision only). Document summaries mask in `documents/summarizer.py`. External translation (Sarvam) is off unless `ALLOW_EXTERNAL_TRANSLATION=True`.
- **Drafting firm set-up** (templates, playbooks) is per firm: query them through `drafting.access.firm_setup(qs, user)`, never `.objects.all()`. Delete archives (`archived_at`); only the creator or a Super Admin may archive/restore (`can_archive`).
- WhatsApp channel is disabled (no real Meta integration).
- **New notification types need a migration.** `notification_queue` / `notification_history` have a live-DB CHECK constraint listing the allowed `type` values; an unlisted type is rejected and the error swallowed in `notifications.service.notify` (tests don't reproduce the constraint). Add the type to `service.EVENT_TYPES`, to the Notifications Center labels, and widen the constraint with a migration like `drafting/migrations/0007_review_notification_types.py` (it reads the current list and adds to it).
- **Draft review** (`docs/DRAFT_REVIEW.md`): whoever has authority over a draft decides, everyone else suggests (`drafting/authority.py`). Review rounds (`drafting/review.py`) apply decisions paragraph by paragraph onto the current draft (`review_apply.py`); the task loop hooks are in `drafting/task_review.py` (called from `workspace/views.py::ReviewTaskView` and `drafting/filing.py`); Request review for task-less drafts is `drafting/review_requests.py`. The draft page's Case file panel (linked case summary + documents) is `drafting/casefile.py`, gated by practice scope + `CASE_VIEW` / `DOCUMENT_VIEW`. A Word file received from outside becomes a suggestions round + comment threads via `drafting/incoming.py` (Import changes). Generated drafts take each clause's alignment from the template / sample (`drafting/services/layout.py`; Word as set, PDF inferred from line positions); `manage.py refresh_template_layout` updates templates uploaded earlier. Tables survive comparison as `Table Row` paragraphs that `export/htmlwrite.py` rebuilds into tables. **Template look** (`drafting/wordform.py`, docs/DRAFT_EXPORT.md): a draft from a Word template / sample opens in its formatting and Download / Save to case write into the original file (`render_draft_docx`; never `render_session_docx` directly for a draft); a PDF upload gets a background Word version (`services/pdf2word.py`, `word_file`) that does the same. **Headings** are split from bodies at upload (`services/headings.py`; slot `heading`/`body`/`heading_kind`, `SampleClause.heading`): the AI writes only bodies (heading given as a label), fixed headings stay as the template has them, variable ones (case details / `[[blanks]]`) are filled by `tasks._fill_variable_headings`. Don't let a prompt ask the model to write a clause heading. Template lines are never put back by rule (that kept stale case details); the prompt's `_LINE_RULE` asks the model to keep fixed lines once and rewrite detail lines in place. In the download, a line with the template's exact words is the template's paragraph copied as-is; letterless layout lines (`))`) and drawn shapes in a clause are kept from the file.
- **Format validation is shared.** GSTIN (pattern, state code, check digit), PAN, PIN code, phone, email and IFSC rules live in `core/validators.py` (server) and `src/utils/validators.ts` (browser). Keep the two in step. A view validates with `check_payload(request.data, {field: kind})`, which returns cleaned data or a 400 `{error, errors}`. A form shows messages with `components/FieldError.tsx`. Empty values are always allowed; "required" is the form's decision. **Phone = Indian mobile**: kind `phone` is exactly 10 digits starting 6-9, saved without +91 (`mobileInput()` keeps a form box to that while typing); an office number that may be a landline uses kind `landline`. **Names** (kind `name`, Client Name): letters in any script, digits, spaces and `. , & / - ' ( )`, 2-150 characters, at least one letter; spaces are tidied. **Due dates / deadlines** being set may be today or later (`due_date_error` / `dueDateError`, optional floor such as the invoice date; give the date input `min={todayISO()}`); existing overdue rows are never re-checked. **Expense / payment amounts** must be above zero (`amount_error` / `amountError`; money boxes get `min="0.01"` and `onKeyDown={blockSignKeys}`). **Passwords** wherever one is set: 8-128 characters, not only spaces, not the email (`password_error` / `passwordError`).
- **AI usage is metered** (`metering` app, `llm_usage`). Any new LLM call must go through `assistant.llm.complete_text` / `stream_answer` or drafting's `LLMProvider.complete`, which record tokens. Wrap the work in `metering.usage.metering(feature, operation, advocate_id)`; otherwise it's recorded as `unattributed`. Report with `manage.py llm_usage`.
- **Security settings fail closed** (`advocate_backend/settings.py`): `DEBUG` defaults to False; without DEBUG the app refuses to start unless `SECRET_KEY` is real (not `django-insecure…`). Tokens are signed with `JWT_SIGNING_KEY` (defaults to SECRET_KEY; changing it logs everyone out). `X-Frame-Options: DENY` + nosniff always; HTTPS flags (`SECURE_SSL_REDIRECT`, `SECURE_HSTS_SECONDS`, `SECURE_COOKIES`, `BEHIND_HTTPS_PROXY`) from env, off on the plain-http LAN.
- **Sessions (Phase 4, `core/jwt.py`, `core/auth.py`, `core/session.py`):** tokens carry `sub`, `advocateId`, `fid` (firm public uuid), `mid` (membership), `tv` (token version), `aud='ams'`; lifetime `JWT_EXPIRATION` capped at `ACCESS_TOKEN_MAX_HOURS` (8). Every request re-validates against the database (user active, version current, claims = the CURRENT active membership, firm ACTIVE in firm mode) and sets `request.firm` / `request.membership`; claims never grant anything. Revocation = bump the account-wide version (`core.session.revoke_all`): logout (ends ALL devices), password change/reset, admin password set, deactivation (`mark_left`), closure, `POST /api/admin/users/<id>/revoke-sessions`, `firms/services.py` suspend helpers. Pre-Phase-4 tokens are refused unless `JWT_ACCEPT_LEGACY_UNTIL` is set. Login refusals after a correct password return `code`: ACCOUNT_DISABLED / NO_ACTIVE_MEMBERSHIP / MEMBERSHIP_SUSPENDED / FIRM_SUSPENDED (wrong password and unknown email look identical). No JWT in URLs: browser tabs/iframes use `POST /api/documents/<id>/link {purpose}` (signed, `DOCUMENT_LINK_SECONDS`, bound to document + purpose + user + session version). Security events go to `audit_log` module AUTH via `core.session.security_event` - never passwords, OTPs, tokens or contents.
- **Platform operators & onboarding (Phase 5, `docs/PLATFORM.md`):** operators are `platform_admin.PlatformOperator` (not advocates), log in at `/api/platform/auth/login` with mandatory TOTP (`core/totp.py`), tokens audience `ams-platform` (refused by the firm API and vice versa), audit in `platform_audit` (firm `audit_log` middleware skips `/api/platform/`). Operator views use `PlatformJWTAuthentication` + `RequireOperator(action)` and must never return firm business data (counts only). No default operator: `manage.py platform_operator create ...`. TOTP seeds are Fernet-encrypted with `PLATFORM_MFA_KEY` (`core/crypto.py`; use `op.get_mfa_secret()` / `set_mfa_secret()`, never the column). New firms only through `firms.provisioning.provision_firm` (idempotent, one transaction, ACTIVE when the admin accepts); invitations only through `firms/invitations.py` (hashed tokens, single use, existing logins prove their password; delivery recorded as SENT/FAILED, never silent; accepting does not sign in).
- **Subscriptions (Phase 8, `docs/SUBSCRIPTIONS.md`, `subscriptions` app):** AMS's own plans, never mixed with the `invoices` app; no payment gateway, no prices. Gate new "add something" paths with `subscriptions.enforce.entitled(key)` / `service.require` (stock limits reserve inside `transaction.atomic`). AI calls: `service.meter(...)` returns a Reservation that MUST be settled (`succeed()` / `fail()` gives the count back / `cancel()`; background jobs `attach('<kind>:<id>')` + `settle_ref`); a reused `Idempotency-Key` is 409, never free. Refusals are 403 `ENTITLEMENT_<reason>`. EXPIRED/CANCELLED/SUSPENDED/PENDING are read-only: never block reads, downloads or login, never delete. **Plans are business decisions:** seeded plans are DRAFT examples; only PUBLISHED plans can be assigned (drafts only to a `test_firm` with `SUBSCRIPTION_TEST_PLANS`, which needs DEBUG); approve/publish/retire/revise only via `/api/platform/plans/<code>` (`plan.publish`, OWNER); never edit an approved plan, make a revision. Every firm has an explicit subscription (new firm without a published plan = PENDING; a firm with no row is refused); `create_firm` is legacy-mode only; `apply_tenancy` assigns Legacy. Plan changes only via `/api/platform/firms/<id>/subscription` (`subscription.manage`, OWNER); PATCH `planCode` answers 400 `USE_SUBSCRIPTION`. Nothing is enforced outside `TENANCY_MODE=firm`. Deploy: `seed_plans`; `run_scheduler` runs `subscription_sweep`; `reconcile_usage` reports (add `--apply` to correct, `--storage` for files). The test runner sends uploads to a temp `DOCUMENT_UPLOAD_DIR`.
- **Login / reset-code guessing** is stopped in `accounts/throttle.py` (table `auth_attempt`, migration `accounts.0001`): 5 wrong passwords per email or 20 per address in 15 min -> 429; 5 wrong reset codes burn every live code. Reset codes are never logged. Until the migration is applied to a database the counters are skipped with an error log rather than breaking login.
- **Firm-level RBAC (Phase 3, `rbac/firm_roles.py`, `rbac/firm_views.py`):** `roles.firm_id NULL + is_template` = immutable system templates; each firm has its own copies (`cloned_from_id`) plus custom roles, names unique per firm (`roles_firm_name_uniq`). The clone of Super Admin is the firm's administrator role (`is_admin`, shown as "Firm Administrator"): needed to grant HIGH_RISK permissions, can't be disabled/deleted, keeps ROLE_MANAGE/USER_MANAGE, and the last active holder can't lose it. Nobody can grant a permission they don't hold. In firm mode `Advocate.effective_role_ids()` counts only enabled roles of the active firm (plus the global Client role) and `has_firm_wide_scope` ignores role names. Role changes write `audit_log` rows (module RBAC, firm_id). New firms: `rbac.firm_roles.provision_default_roles(firm)`. Existing data: `manage.py apply_firm_roles --yes [--allow-database PactPro_db]` (rolls back if any member's permissions would change). Legacy/shadow mode keep the Phase 1 lock (`ROLE_EDITING_LOCKED`) on the shared rows.
- **Backup restore** treats the archive as untrusted: column allow-list + `psycopg2.sql.Identifier`, foreign keys stay on (no superuser `session_replication_role`), references must stay inside the practice, document paths rebuilt from stored names, `BACKUP_MAX_UPLOAD_MB` caps; a documents-only restore writes only the user's own files.
- **Invoices: advocates raise, accounts issue.** Without `INVOICE_ISSUE` an invoice is saved as an `invoices.InvoiceRequest` (`invoice_request`), not an `invoices` row, so it stays out of every total, report, reminder and the client portal until it is issued. Code that reads `Invoice` needs no "pending" filter. `invoices/create` requires `INVOICE_ISSUE`, and issuing replays the request through the same `_create_invoice`. Invoice status is UNPAID / PARTIAL / PAID / CANCELLED: anything that totals or lists money owed must read `Invoice.objects.billable()` (not cancelled) or `.open()` (billable, not paid), and use `core.finance.invoice_balance` for what is still due. A payment against an invoice is linked in `payment_invoice`, then call `recalc_invoice_status`.
- **Money and invoice numbers (Phase 7, `docs/RELIABILITY.md`):** parse/compute amounts with `core/money.py` (Decimal, paise, `parse_amount`, `check_currency`), never float sums. Invoice numbers come only from `invoices.numbering.next_number(advocate, date)` inside the invoice's `transaction.atomic()` (per-firm sequence row locked; unique per firm in the DB, not server-wide). Invoice status changes go through `core.finance.check_invoice_transition` (nothing leaves PAID/CANCELLED). Payments honour `Idempotency-Key` (`invoices.PaymentRequestKey`) and lock the invoice while checking the balance. Sensitive financial changes write `core.audit.business_event(...)`. Client/internal announcements run `on_commit`; tests that need them use `captureOnCommitCallbacks(execute=True)`.
- **Background jobs (Phase 7):** no request context - resolve the firm explicitly (`firm_id_of_advocate`, `firm_active`) and check recipients with `core.tenant.can_receive(advocate_id, firm_id)`. Scheduled reminders claim `notifications.events.claim(...)` (unique `notification_key`) before `notify()`. The drain claims rows PENDING->PROCESSING with one UPDATE and re-checks the recipient before sending; a HEARING_REMINDER carries its hearing's date (`entityDate`) and is cancelled at send time if the hearing has moved or gone. Wrap a job in `core.jobs.job_run(name, firm_id)`; `manage.py job_status` shows runs. Errors recorded are type + first line only.
- **Role names:** Super Admin > Senior Advocate > **Advocate** > Intern (+ Accountant, Receptionist). There is no "Junior Advocate" any more: `manage.py rename_junior_role` renames it and runs on every deploy before the seeds.
- **Permission seeds are deploy steps.** Codes like `INVOICE_ISSUE`, `CASE_ALERTS` arrive through `seed_*_permissions` commands (the `permissions` table is Spring-owned), run on every deploy. Seeds target roles with `rbac.seeding.seed_roles(name)` (the system template + every firm copy cloned from it); revocations use `template_roles` only. Never `Role.objects.filter(name=...).first()`. `manage.py integrity_report` (read-only) flags codes gated in code but missing from the catalogue.
- **Shared reference data with firm-owned links** (acts, and anything like it): list and delete links only through the caller's own cases (`owned(Case...)`), never by the shared object's id alone.
- **Hearings: the next date schedules the next hearing** (`events/scheduling.py`). Event create / update go through `scheduling.check` (before anything is saved) and `save_detail` (one transaction, detail row locked); never write `HearingDetail.next_date` directly. One next hearing per hearing (`next_event_id` unique, moved on a changed date, linked if one already exists that day); DISPOSED or a closed case never schedules one. A real date change of a hearing calls `scheduling.announce_moved` (HEARING_RESCHEDULED to team + client, after commit, read with the row locked so retries don't repeat it).
- **GST place of supply by state codes only** (`invoices/gst.py`): compare 2-digit GST state codes (GSTIN first, then state name/code), never free-text state names; forward charge without both locations, or with an invalid stored firm GSTIN, is a 400, never a guess or a state fallback. Pending tax-policy cases (export, SEZ, multi-state firms, no address on record): `docs/GST_PLACE_OF_SUPPLY.md`.
- **Closed cases** (`cases/closure.py`, docs/CASE_CLOSURE.md): "Closed" carries a reason on the case profile (`closed_reason`): *court_decided* (or none, for older closures) keeps the weekly court check and Appeal Alerts; *no_longer_acting* / *settled* / *other* stop everything that reaches the court or the client. Any new background job that touches a case's court data, reminders or client messages must ask `closure.mode(case)` / `stopped_case_ids()`; never test `status == 'Closed'` on its own.
- **Case money totals are derived columns** on `cases` (`total_paid_by_client`, `total_expenses_so_far`, `balance_in_account`, `pending_from_client`). Any new code that adds, changes or deletes a payment, expense or invoice, or changes a case's fee, must call `core.finance.recalc_case_totals(case_id)`. `manage.py recalc_case_totals` repairs them.

## Frontend architecture

- Entry `src/main.jsx` → `src/App.tsx` (routes). Pages in `src/pages/` (Drafting under `src/pages/Drafting/`), shared UI in `src/components/`, API wrappers in `src/api/` and `src/services/`, state in `src/contexts/`, styles in `src/assets/styles/`.
- Migrated to TypeScript; new files should be `.ts`/`.tsx`.
- **UI: Red Tape design system** (see `docs/UI_REDESIGN.md`).
  - Tokens and component classes are in `src/ui/redtape.css`. React building blocks are in `src/ui/` (`kit`, `forms`, `overlays`, `DataTable`, `Icon`).
  - The shell is in `src/layout/`: the sidebar model is `nav.ts`, and the sidebar and Ctrl+K palette sit next to it. `pages/Dashboard.tsx` hosts the shell and the routes.
  - There is no component library: PrimeReact, PrimeFlex and PrimeIcons were removed. Page-area styles live in `src/ui/pages/*.css` and use only Red Tape tokens. Layout grids use `.cols`.
  - The approved reference prototype is `ams-redesign-demo/PactPro_UI_Redesign_Final.html`.
- **Lint:** `npm run lint` covers `.ts`/`.tsx` too (typescript-eslint parser, `eslint.config.js`). `react-hooks/rules-of-hooks` is an **error**: hooks go above any early `return` (a hook below one blanked the Users page). `exhaustive-deps` is a warning, and lint is clean: keep it at 0. Fix a dependency warning for real when that keeps behaviour. Never just add a function that's re-created every render, because that re-fetches in a loop; use a ref or `useCallback`. If an effect deliberately runs only on certain changes, keep the list and add `// eslint-disable-next-line react-hooks/exhaustive-deps -- <why>`. Type-checking stays with `tsc`: run `npx tsc --noEmit -p tsconfig.app.json` (plain `tsc -p .` checks nothing, the root tsconfig only references the others).
- **Document uploads:** files are written as `.part` then renamed, and removed again if the row isn't saved (`documents/storage.py`); never write a document file outside `create_document` / `add_version`. Allowed types are `documents/storage.py` `ALLOWED_EXTENSIONS` (server, enforced in `create_document` / `add_version`) and `src/utils/fileTypes.ts` (browser pickers, `accept={DOCUMENT_ACCEPT}`). Keep the two lists in step, and the size limit too (`DOCUMENT_MAX_UPLOAD_MB`, default 25 / `MAX_UPLOAD_MB`).
- **Never trust a stored file path.** Open, serve, zip or delete a document file only through `documents.storage.resolve_stored_file` / `remove_stored_file`: they return only paths inside `DOCUMENT_UPLOAD_DIR/documents` (a restored or edited row could point at `.env` or another firm's file) and find rows written on another machine by stored name. Missing file -> 404 `FILE_UNAVAILABLE`.
- **HTML from outside** (mammoth Word previews, Acts text) is rendered only through `src/utils/sanitizeHtml.ts` (DOMPurify). Never add a `dangerouslySetInnerHTML` without it.
- **Copy to clipboard:** always use `copyText()` from `src/utils/clipboard.ts`, never `navigator.clipboard` directly. The office opens AMS over plain http on the LAN, where `navigator.clipboard` does not exist; the helper falls back to `execCommand("copy")` and returns whether it worked.
- **Platform console** (`src/platform/`, routes `/platform/*`): its own axios client and sessionStorage token (`platform/api.ts`); never import the firm `api/client` default or read localStorage `token` there, and firm pages never use `platformApi`. Guard pages with `PlatformRoute permission=...`.
- **UI tests:** `npm test` (Vitest, jsdom, `vitest.config.ts`, setup `src/test/setup.ts`, tests in `src/__tests__/`). Wrap pages that use `AuthFrame` in `ThemeProvider`; mock the firm API with `vi.mock('../api/client')`.
- **Client portal routes:** clients sign in at `/client/login` and use `/client/*` (`client/ClientApp.tsx`); staff use `/login` and `/dashboard`, and each side is redirected to its own home (`App.tsx`). Portal links are built only by `clientaccess.views.portal_url` (it adds the signed firm key `?f=` that brands the sign-in page); never hand-build `/client/...` links in the backend.
- **Hover hints:** use the native `title` attribute (plus `aria-label` on icon-only buttons); there is no tooltip component.
