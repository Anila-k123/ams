**Date:** 2026-10-01 · **Branch:** `Developer-1` (commit `1597b5f`) · **Mode:** read-only (no code, schema or dependency changes)

**Method.** I split the repository into six parallel reviews:
1. backend, API and database
2. authentication, RBAC and tenant isolation
3. core legal workflows
4. frontend and UX

**Paths.** `BE/` = `Advocate-app-BE-Django/`, `FE/` = `Advocate-app-FE-main/src/`.

## 1. Executive Summary

| Dimension | Assessment |
|---|---|
| **Platform maturity** | Feature-rich late prototype or early beta. Broad coverage of what an advocate needs: cases, clients, hearings, tasks with senior review, documents with versions and AI summaries, invoices with GST, payments, expenses, reports, client portal, court data (cause lists, display boards, eCourts), appeals detection, acts and law codes, AI assistant, legal drafting. |
| **Architecture quality** | A pragmatic Django monolith with a React SPA. It is sound overall, but carries a lot of legacy from the Spring-era schema: 26 of 37 core models are `managed=False`, with plain-integer IDs instead of foreign keys, float money columns and free-text statuses. The "practice" data-isolation model (`core/practice.py`) is a good idea and is applied consistently in the core create/read/update/delete views. |
| **Code quality** | Mixed. The backend has thoughtful comments, real-database behavioural tests and a deny-by-default client-portal gate. The weaknesses are no service layer, request bodies parsed by hand instead of validated, and some very large files. The frontend has 2,000-line components, 626 uses of `any`, TypeScript that is not linted, and zero tests. |
| **Security posture** | **Not safe for multi-firm production.** One CRITICAL cross-tenant account-takeover path (the admin user API is not scoped to the firm). A CRITICAL JWT-forgery risk from the default `SECRET_KEY`. Several HIGH issues: password-reset OTP can be brute-forced, SQL injection in backup restore, cross-tenant leaks in the drafting and acts modules, no upload validation, and a credential in git history. |
| **Production readiness** | **Not ready.** No CI, no Docker, no rate limiting, no automated backups. Jobs run as in-process stopgaps, the scheduler is unsupervised, and the defaults are insecure. |
| **Biggest risks** | (1) One firm's admin can take over another firm's accounts and data. (2) Forged tokens if the default key reaches production. (3) Billing correctness: float money, payments never linked to invoices, numbering races. (4) Confidential client data sent to third-party LLMs with no consent or redaction. (5) No backup or disaster-recovery automation for a legal-records system. |
| **Biggest opportunities** | The domain coverage is already large, so most of the value lies in hardening, not new features: tenant scoping on admin, drafting and acts; validation; money correctness; scheduling and notification reliability. After that, a strong "advocate's morning brief" (today's hearings, overdue tasks, dues) and structured hearing outcomes that drive the next hearing date. |

## 5. System Architecture

```
Browser (React SPA, JWT in localStorage)
   │  axios (Bearer) / some raw fetch / ?token= for file links
   ▼
Django + DRF  (runserver / waitress / gunicorn)
   ├─ AuditLogMiddleware (POST/PUT/PATCH/DELETE → audit_log)
   ├─ AdvocateJWTAuthentication → left_on check → clientaccess.gate (portal allowlist)
   ├─ RequirePermission('CODE')  (role→permission via advocate_roles/role_permissions)
   ├─ Views (business logic mostly inline) → practice_ids(user) row scoping
   ├─ ORM → PostgreSQL (public = AMS legacy+Django tables, drf = drafting + pgvector)
   ├─ Local disk: DOCUMENT_UPLOAD_DIR, DRAFTING_MEDIA_ROOT, court_pdf_cache, backups
   ├─ In-process: summary daemon threads, drafting ProcessPool, inline SMTP (send_now)
   └─ Outbound HTTP: court scraper (:8000), LLM providers, SMTP
Separate processes: manage.py run_scheduler (scan + drain), Task Scheduler .bat jobs (optional, not registered here)
```

**Data isolation rule.** A row is visible when its `advocate_id` is in `practice_ids(user)` = {practice owner} ∪ {members}. Permissions then decide which actions are allowed. Tasks have an extra rule (`workspace/access.py`): only users with `TASK_ASSIGN` see all of the firm's tasks; everyone else sees only tasks assigned to them or created by them.

## 6. Domain Model

| Entity | Table | Main relationships | Key problems |
|---|---|---|---|
| Advocate (user) | `advocate` | `parent_advocate_id` (plain integer) → practice owner | God-model (35+ columns); `role` string duplicates the RBAC tables; no timestamps; `parent_advocate_id` is not a foreign key. |
| Client | `clients` | Foreign key to advocate | Name, email and phone all nullable; no uniqueness; `created_at` is a DATE; soft delete only via a flag. |
| Case | `cases` | Foreign keys to advocate and client (nullable) | **Money stored as float**; stale denormalised totals (`total_paid_by_client` etc. are never written); free-text `status`, `case_type`, `court_level`; unique (advocate, case_number) but not per practice. |
| CaseEvent (hearing) | `case_events` | Foreign keys to case and advocate | Free-text type; no unique key, so duplicates already exist in the DB; `notified` flag is never set. |
| HearingDetail | `hearing_detail` | One-to-one with event via plain integer | Purpose, outcome and next date are not used to drive the workflow. |
| CaseTask (+ submission, document) | `case_task` | Plain integer `case_id`, `assigned_to_id` | No foreign keys, so orphans are possible; the legacy `tasks` table is dead. |
| Note / Tag / Party / Related | `case_note` etc. | Plain integer `case_id` | No foreign keys. |
| Document (+ version, summary) | `documents`, `document_version`, `document_summary` | Foreign keys to advocate, case and client | Absolute `file_path` stored in the row; version counter duplicated; hard delete. |
| Invoice (+ items, tax) | `invoices`, `invoice_items`, `invoice_tax_detail` | Foreign keys to case, client, advocate; children via plain integer | Float money; numbering is global across all firms; `status` is UNPAID/PAID only. |
| ClientPayment | `client_payments` | Nullable foreign keys | Float money; **no link to an invoice**; no update or delete endpoint. |
| Expense | `expenses` | Foreign keys | Float money; free-text status and mode. |
| Role / Permission | `roles`, `permissions`, join tables | Plain integers (DB unique constraints exist) | **Roles are global, not per firm.** |
| Notification family | `notifications`, `notification_queue`, `notification_history`, `notification_log`, templates | Plain integers | Four overlapping tables with redundant columns. |
| Audit | `audit_log`, `activities`, `case_timeline_event` | Plain integers | Three overlapping event logs. |
| Drafting | `drf.*` | Case link by plain integer | Template, Playbook and PlaybookClause have **no tenant column**. |

**Assessment.** The model covers legal case management reasonably well: matters, parties, hearings with outcome and next date, delegated work with review, billing with GST. Its weak points are integrity and lifecycle:
- **No foreign keys** across the Django-managed tables.
- **No created_by / updated_by** fields: `advocate_id` stands for "creator", even inside shared practices.
- **Soft delete is inconsistent**: cases and clients are soft-deleted, but documents, events, expenses, notes and tasks are hard-deleted.
- **No status enums or state machines.**
- **Money handling**: float columns, and invoices and payments are not linked.

## 7. Core User Workflows (traced)

**Login**
- `Login.tsx` posts to `/api/advocates/login` (`accounts/views.py LoginView`, AllowAny).
- The server checks bcrypt and `left_on`, then issues a JWT.
- The frontend stores the token in `localStorage`; the axios interceptor attaches it as a Bearer header; `PermissionContext` fetches `/my-permissions`.
- Gaps: no throttling, no lockout, no token revocation.

**Create a case**
- `AddCase.tsx:1087` → `POST /api/cases/create` → `CreateCaseView` (`CASE_CREATE`).
- The view parses `request.data` by hand, checks the client is in the practice, and checks for a duplicate within the practice (check-then-insert, no transaction).
- Then `Case.objects.create`, the `client_events.case_created` email (sent inline), and an audit row from the middleware.
- Gaps:
  - A race on case number.
  - An `IntegrityError` returns 500 instead of 409.
  - No normalisation of case numbers.
  - Reviving an archived case deletes **all** of its hearings, including ones entered by hand.

**Schedule a hearing**
- `HearingsPage.tsx:144` / `CaseDetail.tsx` → `POST /api/events/create` → `CreateEventView`.
- The view checks the case is in the practice, creates the `CaseEvent`, upserts `HearingDetail`, then sends `hearing_scheduled` (to the client) and `hearing_added_team`.
- Gaps:
  - No duplicate or conflict check.
  - Over-long purpose or bench values cause a 500.
  - An update sends no notification.
  - No hearing status.

**Upload a document**
- `DocumentsPanel.tsx` → `/api/documents/upload` → `storage.create_document` → `_write_file` writes `uuid + original extension` to disk.
- The `documents` row then starts a summary daemon thread, which sends the text to the LLM.
- Gaps: no type or size validation; preview is served inline with the content type the client supplied.

**Delegate a task**
- `CreateTaskView` → `SubmitTaskView` (assignee) → `ReviewTaskView` (assigner or `TASK_ASSIGN`, never the assignee) → `review.approve` (task completed, documents marked APPROVED) → notifications.
- Controls are good. Gaps: `DeleteCaseTaskView` lets the assignee delete the task, and the transitions are not atomic.

**Bill a client**
- `CreateInvoiceView` (`INVOICE_CREATE`) → `_next_invoice_number` scans every invoice in the system → creates the invoice, items and tax detail **without a transaction** → `invoice_generated` email sent inline.
- `PayInvoiceView` only flips the status to PAID: no payment record and not idempotent, so calling it twice resends the emails.
- `CreatePaymentView` records a payment with no link to any invoice.

**Client portal**
- An invite token (256-bit, hashed, 72-hour expiry) → set password → a CLIENT advocate row → `clientaccess.gate` allows only `/api/client/*` → `scope.py` filters to that client's own cases, invoices, payments and shared documents.
- This is the best-designed flow in the codebase.

**Reminders**
- `run_scheduler` (must be started by hand) → `scan_notifications` raises hearing reminders 2 days ahead, overdue invoices every 7 days forever, and overdue tasks every day forever → `notification_queue` → `process_notifications` sends them.
- Gaps: no claim on queue rows, so the same notification can be sent twice; only 2 retries actually happen; no scheduler is registered on this machine.

## 8. Backend Audit

**Architecture**
- Fat views with no service layer. Business logic lives in views; for example GST and invoice numbering are in `invoices/views.py`.
- Some well-factored modules exist: `core/practice.py`, `notifications/*`, `cases/timeline.py`, `drafting/services/*`.
- Largest files:

| File | Lines |
|---|---|
| `drafting/tasks.py` | 1,220 |
| `courtsearch/views.py` | 1,107 (about 40 views) |
| `workspace/views.py` | 699 (30+ views) |

**Validation**
- Serializers are used mainly as read-only DTOs. Writes parse `request.data` by hand: `amount`, dates and lengths go unchecked.
- Result: bad input causes 500s, not 400s (cases, events, invoices, payments, expenses).

**Errors**
- There is no custom `EXCEPTION_HANDLER`, so three error shapes coexist: `{'error'}`, DRF `{'detail'}` and field dicts.
- Some success responses are bare strings.
- There are 92 `except Exception` blocks (untriaged).

**API conventions**
- Verbs in URLs (`cases/create`, `update/<id>`, `delete/<id>`) and an inconsistent URL space.
- Missing endpoints: invoice edit/void, payment edit/delete.
- About 20 list endpoints are **not paginated** (`cases/my-cases`, `events/today|upcoming|my-events`, `documents/list|filter|by-case`, `notifications`, `workspace/tasks/all`, `invoices/my-invoices`, `expenses/*`, …).
- `SpringStylePagination` silently clamps an out-of-range page to the last page.
- There is no API versioning.

**Concurrency**
- Only some paths use transactions: case transfer, drafting filing (`select_for_update`), cause-list sync, client access.
- Core create/update/delete has no transactions and no optimistic locking, so the last write wins.

**Migration drift (HIGH).** `makemigrations --check` reports a pending migration, `acts 0002_actpaper`. The table `acts_actpaper` (5,486 rows) already exists in the database but has no committed migration. A fresh `migrate` will not create it, and a future migration for it would fail on the existing database.

**Schema evolution outside migrations.** Management commands such as `enable_shared_practice` and `scope_case_numbers` run DDL directly, so `migrate` alone cannot rebuild a database. There is also no schema script for the Spring-owned tables.

## 10. Database Audit

**Integrity**
- Primary keys exist, and the DB has real foreign keys on the Spring tables. However, the Django ORM declares them `DO_NOTHING`.
- The Django-managed tables use plain integers instead of foreign keys (workspace, RBAC, audit, notifications, drafting).
- Uniqueness:

| Constraint | Status |
|---|---|
| `(advocate_id, case_number)` | Exists; stricter per-practice uniqueness is enforced only in application code. |
| `invoice_number` | Globally unique, shared across all firms. |
| Clients | No uniqueness. |
| `case_events` | No uniqueness; **3 duplicate hearing sets already exist** in the data. |

- No `updated_at` on most tables, no `created_by`, and `created_at` is a DATE on cases and clients.

**Money**
- Every amount is a float (`double precision`): cases, invoices, items, tax, payments, expenses.
- Python's `round()` uses banker's rounding on binary floats, which conflicts with GST rounding conventions.

**Indexes**
- The main foreign-key, date and status composites are covered.
- **No trigram (`pg_trgm`) indexes on `cases` or `clients`** even though search uses `ILIKE '%q%'`. The `acts_*` tables already use trigram indexes, so the pattern is known in this codebase.
- No `(case_id, date)` composite on `case_events`.

**Query patterns**
- N+1 queries in `notifications/views.py:97-103` (two queries per history row).
- Aggregation done in Python loops in invoice summary, monthly expenses, document stats, tags, the dashboard (which loads *all* cases, events, invoices, payments and expenses on every load) and the timeline (built fully in memory, then paginated).
- `_next_invoice_number` loads every invoice number in the system on each create.

**Migrations**
- `acts` drift (see §8).
- DDL lives in management commands.
- Tests build tables from the models without running migrations (`core/test_runner.py`), so the live CHECK constraints are never exercised by tests.

## 11. Authentication Audit

| Control | State |
|---|---|
| Password hashing | bcrypt, 10 rounds. ✔ |
| JWT | HS256 with the algorithm pinned. ✔ Signed with `SECRET_KEY`, which **defaults to a public literal, and the local `.env` uses that same default** (S-02). |
| Expiry / refresh | 24-hour token, no refresh token. Logout does nothing on the server. Changing or resetting a password does **not** revoke existing tokens. |
| Departed members | `left_on` is checked on every request and on `?token=` downloads. ✔ |
| Password-reset OTP | 6 digits, SHA-256 with a salt, 10-minute TTL, 5 issued per hour. **No limit on verification attempts** (brute-forceable), and the **OTP is logged in plaintext** (`accounts/otp_views.py:55`). |
| Rate limiting / lockout | **None.** No DRF throttles are configured. |
| Password policy | Inconsistent. `reset_password` accepts an empty password. Settings, admin and signup have no minimum length. Only some paths require 8 characters. |
| Token transport | `localStorage` plus `?token=` in document URLs, so the token leaks through history, logs and the Referer header. |
| CSRF | Not applicable (Bearer token, no cookies). ✔ |
| Account enumeration | A 429 "too many OTP requests" response only for real accounts; login timing differs; a duplicate email on profile update returns 500. |
| Mass assignment | `role` and `email` can be written through the self-service profile serializers. |

| **Admin user / role API** (`rbac/views.py:217, 266, 272, 323`, `_resolve_practice_owner:185`) | ✘ **CRITICAL.** Lists, edits, resets passwords for, re-roles, deletes or *moves into the caller's own practice* any advocate in any firm. ## 13. Case Management Audit

- **Status.** Free text. The UI offers Active, Pending and Closed; the dashboard and reports also count `dismissed`, which nothing ever produces.
- **No case history.** Nothing records status changes, transfers or closure. `case_timeline_event` is legacy and the timeline fakes a single "closed" entry. The notification types `CASE_STATUS_UPDATED`, `CASE_CLOSED` and `HEARING_RESCHEDULED` are declared but never emitted.
- **Case numbers.** Uniqueness is enforced per practice but not normalised (`WP 123/2024` and `wp123/2024` count as different). Renaming to a duplicate causes a 500.
- **Archiving.** Archive is a soft delete with no checks for open tasks, unpaid invoices or future hearings. Reminders keep firing for archived cases, because `notifications/events.py` does not filter on `case__deleted`.
- **Reviving an archived case** deletes every hearing on it, including manual ones (`_clear_import_children`).
- **Transfer.** Atomic and thorough for cross-team moves, but it records no reason or history and does not notify anyone of a same-team transfer.
- **Stale money columns.** `cases.total_paid_by_client`, `pending_from_client` and related columns are never updated, yet the client portal shows "fees agreed/paid/pending" from them.
- **Truncation.** `varchar(255)` on title and description causes a 500 when exceeded.
- **Recommended lifecycle.** `Draft → Active (Pending/Stayed/Reserved) → Disposed → Closed → Archived`, as an enum, with a status-history table and notifications on change. The "Stayed" and "Reserved for judgment" states matter in Indian practice.

## 14. Client Management Audit

- **Deduplication on create.** Matches the same name case-insensitively plus an email or phone match within the practice. The phone is reduced to digits only, so `+91 98765 43210` and `098765 43210` don't match.
- **Updates.** No dedup check on update and no DB uniqueness.
- **Search.** Unindexed `ILIKE`, and phone search isn't normalised.
- **Archiving a client** leaves their cases, invoices and portal logins untouched.
- **Portal exposure.** The client portal shows the internal case `description`, opposing counsel, hearing outcomes and the firm's email bodies. Confirm this is intended, or add client-safe fields.
- **Impersonation.** A Receptionist with `CLIENT_EDIT` can generate an invite link and so set the client's password.

## 15. Hearing / Calendar Audit

- **Data.** Hearings live in `case_events` plus `hearing_detail` (purpose, court, bench, judge, next date, outcome). Only 7 of 136 events have a time.
- **Lifecycle.** No hearing status (scheduled, adjourned, heard). `next_date` doesn't create the next hearing, and `outcome` doesn't update the case.
- **No duplicate or conflict detection.** Duplicates are already in the data.
- **Timezones.** `USE_TZ=False`, `Asia/Kolkata`, naive datetimes, and `date.today()` follows the OS timezone. Safe only while the server runs in IST.
- **Reminders.**
  - Sent 2 days ahead, for `HEARING` events only, to staff with `CASE_ALERTS`.
  - Clients get no pre-hearing reminder.
  - The `CaseEvent.notified` flag is never set, which makes the "missed hearings" report count almost every past hearing (130 of 132).
- **Calendar.** `react-big-calendar` shows month and week views. There is no list or filter view, and no iCal, Google or Outlook sync.
- **Cause-list sync** (`sync_causelist`) is a sound design, but **not scheduled anywhere** (no `.bat`, no task). The "Your items" feature therefore stays empty unless someone runs it by hand.

## 20. Privacy & Legal Data Protection

- **Third-party LLM disclosure (HIGH).** With `LLM_PROVIDER=openai|gemini`, every assistant question sends case summaries, hearings, parties, up to 20 notes, client details and practice finances, and every upload sends up to 24,000 characters of document text (`assistant/tools.py build_context`, `documents/summarizer.py`). There is no redaction, consent or per-firm opt-in; a grep for `consent|retention|gdpr` finds nothing. The default `local` provider goes through a public ngrok tunnel, and its API key is optional.
- **Prompt logging (HIGH).** `drafting/providers/llm.py` logs the full system prompt, user prompt and response at INFO level.
- **Plaintext secrets at rest.** SMTP password and WhatsApp token in `communication_settings`.
- **Encryption.** In transit depends on the reverse proxy (no HSTS). At rest: none for files or fields.
- **Client documents in git.** 4 uploaded PDFs are tracked in git.
- **Audit gaps.** Reads are not audited, so document downloads (staff side), case views and failed logins aren't recorded. The client portal does audit its own downloads.
- **Retention.** No retention or legal-hold policy beyond the audit-log prune.
- **India-specific.** DPDP Act 2023 obligations (consent, purpose limitation, breach notice) should be assessed by counsel. This is a legal question, not a code finding.

## 21. Performance Audit

At current data volumes (25 cases, 10 clients) performance is fine. At scale:
- the dashboard loads every row of 5 tables into Python on each view;
- about 20 list endpoints are unpaginated;
- search is `ILIKE '%q%'` with no trigram index;
- several aggregations run in Python;
- the timeline is built fully in memory;
- the notifications history has an N+1;
- invoice numbering scans the whole table;
- inline SMTP and LLM calls hold request workers (LLM timeout 600 s, cause-list proxy 300 s);
- the assistant runs about 12 queries per question.

On the frontend: large PNGs, 377 KB of eager CSS, recharts loaded on the landing page, and no request de-duplication.

## 22. Scalability Audit

| Scale | Verdict |
|---|---|
| 10 advocates, 1 firm | Works today, once the S-02 and S-03 fixes are in. |
| 100 advocates / several firms | **Blocked by tenant leaks** (S-01, S-06, S-07), plus global invoice numbering and global roles. Unpaginated lists start to hurt. |
| 1,000 advocates | Needs: Redis cache and a Celery worker (not LocMem or in-process jobs), Python aggregations moved into SQL, trigram/full-text search, object storage for files, and a supervised scheduler. |

**Horizontal scaling is currently unsafe:**
- the cache is per process;
- each web worker spawns its own drafting process with 1–2 GB of models;
- summary threads are lost on restart;
- the notification drain would double-send.

Microservices are **not** recommended. A monolith plus a worker plus Redis is enough.

## 24. Logging & Observability

- **Logging.** Console only; two named loggers (`accounts`, `drafting`). No request IDs, no structured logs, no file rotation.
- **Monitoring.** No Sentry and no metrics.
- **Sensitive data in logs.** The OTP and the full drafting prompts are logged; both must stop.
- **Audit log.**
  - **Strengths:** a middleware records mutations with field diffs and masks sensitive fields; `prune_audit_log` handles retention well.

## 36. Architecture Recommendations

**Keep**
- The Django monolith with DRF.
- The React SPA.
- PostgreSQL as the only data store.
- The `practice_ids` scoping model.
- `RequirePermission`.
- The client-portal gate.
- The notification queue concept.

**Change (incrementally)**
1. **One tenancy helper.** Add `scoped(qs, user)` / `get_scoped_or_404` and use it everywhere, including admin, drafting and acts. Add a test that walks every URL to check that cross-firm IDs return 404 (extend `core/tests.py`).
2. **Services and validation.** Use DRF serializers for input and `services/` modules for case, invoice, hearing and transfer logic, each wrapped in `transaction.atomic`.
3. **Worker tier.** Redis, plus a Celery worker for summaries, drafting, email sending and scraper calls, plus Celery beat replacing `run_scheduler` and the `.bat` files.
4. **Ledger.** Decimal money; `payment → invoice` allocation; a per-firm invoice sequence.
5. **Files.** A storage abstraction (local now, S3-compatible later), with signed short-lived download URLs instead of `?token=`.
6. **Settings.** Split into `settings/base.py` and `prod.py`, with fail-closed checks.

**Target shape**

```
SPA ──HTTPS──► nginx/IIS ──► Django (gunicorn/waitress, N workers, stateless)
                                ├─ Postgres (Decimal money, FKs, trigram)
                                ├─ Redis (cache + broker)
                                └─ Celery worker(s) + beat ──► SMTP, LLM, scraper, drafting models
Backups: nightly pg_dump + file sync, restore drill monthly
```
